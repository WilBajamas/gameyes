# Flutter state management — QuestLoggd conventions

Covers the state layer only. For the widgets that consume this state, see the
`flutter-widgets` skill. For the use cases a BLoC/Cubit calls into, see
`flutter-usecase`.

---

## BLoC vs. Cubit

- **BLoC** — when there are discrete named events (e.g. `GamesFetched`,
  `GamesNextPage`).
- **Cubit** — when state is driven by plain method calls, no event queue.

## Naming and file shape

- BLoC file `[feature]_bloc.dart`, class `[Feature]Bloc extends Bloc<[Feature]Event, [Feature]State>`.
- Cubit file `[feature]_cubit.dart`, class `[Feature]Cubit extends Cubit<[Feature]State>`.
- Both annotated `@injectable`.
- State file `[feature]_state.dart`.
- Events (BLoC only): base `sealed class [Feature]Event extends Equatable`,
  each event `final class [Feature][Action] extends [Feature]Event`
  (`GamesFetched`, `GamesNextPage`), defined as a `part` file of the BLoC
  (`part of '[feature]_bloc.dart';`).

## State class convention

```dart
enum GamesStatus { initial, loading, success, failed, empty }

@freezed
sealed class GamesState with _$GamesState {
  const factory GamesState({
    @Default(GamesStatus.initial) GamesStatus status,
    GameListEntity? response,
    ErrorType? error,
  }) = _GamesState;
}
```

- `@freezed sealed class`, single `const factory`, always has `copyWith`
  (generated by freezed).
- Status tracked by a feature-specific enum — never a boolean.
- Errors stored as `ErrorType?`, never `String?` or `Exception?`.
- Every field has `@Default(...)` where a sensible default exists.

## Handler convention (BLoC)

- Handlers registered in the constructor: `on<Event>(handler, transformer: ...)`.
- Use `bloc_concurrency` transformers: `droppable()` for a fetch, `sequential()`
  for a mutation.
- Result handled via an exhaustive `switch` **expression** (not statement) —
  every variant explicit, no `default:`:
```dart
final newState = switch (result) {
  Success(value: final response) => state.copyWith(
      status: GamesStatus.success,
      games: response.items,
    ),
  Failure(error: final error) => state.copyWith(
      status: GamesStatus.failed,
      error: error,
    ),
};
```
This same exhaustive-switch pattern applies anywhere else a sealed class
(like `Result<T>`) needs to be unwrapped — use cases and repositories included.

## Provisioning in screens

Provide at the screen level using `BlocProvider` + `getIt` — never above the
screen, always scoped to the smallest subtree that needs it:
```dart
BlocProvider(
  create: (context) => getIt<GamesBloc>(),
  child: Scaffold(...),
)
```
- `context.read<T>()` — inside callbacks, does not subscribe.
- `context.watch<T>()` — inside `build`, full rebuild on every state change.
- `BlocBuilder<B, S>` — preferred for conditional rebuilds.
- Never pass a BLoC/Cubit down the widget tree as a constructor parameter.
- Never `BlocProvider.of<T>(context)` — use the extension methods.

Don't add `listenWhen` to a `BlocListener` as a reflex. If the listener body
already guards the condition itself, a matching `listenWhen` is redundant —
skip it. Only add it when it changes real behaviour: skipping otherwise-
non-idempotent work, or acting as the sole guard against an unwanted call.

## Reactive boundary convention

- Put `BlocBuilder`, `BlocSelector`, and `BlocListener` at the **lowest**
  widget-tree boundary that consumes the relevant state.
- Keep static route/layout shells — `Scaffold`, `SafeArea`, scroll views,
  slivers — outside that boundary unless their own properties depend on state.
- Do not create a passthrough view class merely to hold a builder or return
  another widget. Let the screen own its static composition directly.

## Status-driven UI rendering pattern

Use `if`-guarded slivers/widgets driven by the state's status enum. Never a
`switch` on `state.status` for top-level layout selection — `if` lets
multiple states coexist (e.g. content + next-page loader visible together):

```dart
CustomScrollView(
  slivers: [
    if (state.status == GamesStatus.loading)
      const SliverFillRemaining(child: GameItemGridLoadingShimmer()),

    if (state.status == GamesStatus.success)
      const GamesSliverGrid(),

    if (state.nextPageStatus == GamesNextPageStatus.loading)
      const SliverToBoxAdapter(child: CircularProgressIndicator()),

    if (state.nextPageStatus == GamesNextPageStatus.failed)
      SliverToBoxAdapter(child: ErrorRetryWidget(...)),

    if (state.status == GamesStatus.failed)
      SliverFillRemaining(child: Center(child: ErrorRetryWidget(...))),
  ],
)
```
`SliverFillRemaining` for full-screen states, `SliverToBoxAdapter` for inline
ones.

## Pagination pattern

Trigger the next page at **90% of `maxScrollExtent`** via
`NotificationListener<ScrollUpdateNotification>`.

State tracks two separate statuses — never collapse into one:
- `status` — initial load (`loading`, `success`, `failed`, `empty`)
- `nextPageStatus` — subsequent pages (`initial`, `loading`, `failed`)

On next-page success, append: `games: List.of(state.games)..addAll(response.items)`.
Page tracked as `currentPage` (starts at 1). Check `state.response?.nextUrl`
before triggering another page. `droppable()` transformer on both the fetch
and next-page events.

## Pull-to-refresh pattern

`CupertinoSliverRefreshControl`, shown only when `status == success`:
```dart
if (state.status == GamesStatus.success)
  CupertinoSliverRefreshControl(
    onRefresh: () async => context.read<GamesBloc>().add(const GamesFetched()),
  ),
```

## What NOT to do

- Do not use `switch` **statements** for top-level layout selection — `if`
  guards instead
- Do not collapse `status`/`nextPageStatus` into one enum
- Do not show pull-to-refresh outside `status == success`
- Do not pass a BLoC/Cubit as a constructor parameter
- Do not provide a BLoC/Cubit above the screen that needs it
- Do not add `listenWhen` unless it changes actual behaviour
