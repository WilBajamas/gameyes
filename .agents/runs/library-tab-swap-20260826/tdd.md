The shape of the design did not change — three parallel declaration orders, one

## Feature summary

A presentation-and-routing-only change. The bottom tab set stays at five and is
reordered to `Featured(0) · Library(1) · Browse(2) · Feed(3) · Settings(4)` by
rewriting three parallel declaration orders that must agree —
`BottomTabBarDestination`'s values, `AppRouter`'s `HomeRoute` children, and
`AutoTabsRouter`'s `routes:` list in `home_screen.dart` — and regenerating
`auto_route_config.gr.dart` from the second of them. Tab index is derived, never
declared, so the six hard-coded `setActiveIndex` literals are rewritten in the same
change and a seventh is introduced by a new throwaway `LibraryScreen`. Slot 2 is
the existing Games screen under a new *label only*: its feature folder, bloc,
repository, datasource and class name are untouched, and only its app-bar title
string moves. A second new screen, `FeedScreen`, is a deliberately barer
placeholder. Three source files retire, four `.arb` keys change and the `S` class
is regenerated by `intl_utils`. One two-line correction lands in a skill file. No
data, domain or state layer is added or touched.

## UI layer

### Screens

**`LibraryScreen` (create)** — `lib/features/library/presentation/screens/library_screen.dart`
— `StatelessWidget`, `@RoutePage()`, **`const` constructor**. Consumes nothing but
`S`. Structure: `Scaffold > SafeArea > CustomScrollView` with two slivers —
`DefaultSliverAppBar(title: S.current.library)` and a padded `SliverToBoxAdapter`
holding one `EmptyStateCard`. One interaction: the card's action calls
`AutoTabsRouter.of(context).setActiveIndex(2)` — Browse, i.e. the Games screen.
Navigates nowhere else. No reactive boundary exists because there is no state.

**`FeedScreen` (create)** — `lib/features/feed/presentation/screens/feed_screen.dart`
— `StatelessWidget`, `@RoutePage()`, **`const` constructor**. Consumes nothing but
`S`. Structure: `Scaffold > SafeArea > CustomScrollView` with two slivers —
`DefaultSliverAppBar(title: S.current.feed)` and a `SliverFillRemaining` holding
`Center(child: Text(S.current.coming_soon))`. **No `EmptyStateCard`, no glyph, no
action, no button, no `setActiveIndex` call, no `ScrollController`**
([3.2-AC32], [3.2-AC33]). The asymmetry with Library is a human decision at the
Phase 3 gate, not an oversight: Library's empty state is the thing item 4.5
evolves, Feed's placeholder is thrown away whole.

`SliverFillRemaining(hasScrollBody: false)` rather than `SliverToBoxAdapter` is
the one structural call here — a `SliverToBoxAdapter` wrapping a `Center` hugs
its child and centres nothing vertically, which is the bug the deleted
`browse_screen.dart:51-53` shipped. This is structure, not layout design: no
size, colour or spacing is chosen.

The `const` constructor on both is load-bearing, not style: auto_route emits
`PageRouteInfo<void>` with no args class for a `const` screen (see `BrowseRoute`
at `auto_route_config.gr.dart:110-122`) and a `PageRouteInfo<XRouteArgs>` plus an
args class for a non-`const` one (see `TrackerRoute` at `:406-446`). A non-`const`
screen still compiles but ships a pointless `LibraryRouteArgs` / `FeedRouteArgs`.

**`GamesScreen` (modify — one string)** — `lib/features/games/presentation/screens/games_screen.dart:171`
— `GamesAppBar`'s `title:` goes `S.current.games` → `S.current.browse`
([3.2-AC35]). `:172`'s `subtitle: S.current.games_screen_subtitle` is a separate

**`FeaturedScreen` (modify)** — `:144`, `:145`, `:147` (all `1`) and `:207` (`3`)

**Deleted:** `tracker_screen.dart`, `browse_screen.dart` (and the now-empty

## Routing — the route path decision for slot 2

[3.2-AC4] leaves the slot-2 **path** to me: `games` or `browse`. Deciding it:

**The path stays `games`.** Reasons, in order of weight:

1. **The path is code-facing, and D6 scopes the relabel to user-visible surfaces
   only.** Android declares no `VIEW` intent filter, so a URL naming this path
   cannot be delivered to the app at all — no user, no link, no bookmark and no
   analytics reads it. Under [3.2-AC36] every code-facing identity stays `Games`:
   the folder, the class, the bloc, the repository, the datasource and the
   generated `GamesRoute`. A `browse` path would be the single code-facing name
   that moved, which is the opposite of the rule D6 states.
2. **It would create a fresh mismatch on one line.**
   `AutoRoute(path: 'browse', page: GamesRoute.page)` reads as a mistake to the
   next person, and there is nowhere to put the explanatory comment, because the
   project's comment rule would delete it. Keeping `games` makes path and page
   agree, and the *label* is the thing that differs — which is exactly the story
   D6 tells.
3. **The rename is already scheduled to happen coherently.** The human's stated
   end state is that this screen becomes Browse in name too, in a later week,
   under new conventions. The path moves then, in one diff with the folder and the
   class, instead of being split across two items.
4. It is zero diff and zero risk in an item whose real risk is ordering.

Nothing in the criteria, the tests or the app depends on this either way; it is
recorded so it is a decision on the record rather than an omission.
`RouteConstants.games` (`lib/core/res/const.dart:61`) is **unrelated** to this —
it is a hero-tag `fromScreen` discriminator used by `games_screen_test.dart:116`,
not an auto_route path, and it is not touched.

## Ordering — the actual risk in this item

Three declaration orders must agree and one generated file is derived from one of
them. Sequence so no intermediate state can leave them disagreeing *at a point where
anything is checked*:

1. **`.arb` edits, then `intl_utils:generate`, first.** Everything downstream reads
   `S.current.library` and `S.current.feed`, and the two deleted getters
   (`games`, `tracker`) must be gone before the enum, the Games app bar and the
   tab-bar test are rewritten to stop naming them.
2. **The two new screens, then the three deletions, then the Games title.**
   `LibraryScreen` and `FeedScreen` must exist with `@RoutePage()` before the
   router config names `LibraryRoute.page` / `FeedRoute.page`, and
   `browse_screen.dart` / `tracker_screen.dart` must be *gone before* the router is
   regenerated — otherwise their `@RoutePage()` annotations keep emitting
   `BrowseRoute` / `TrackerRoute` / `TrackerRouteArgs` into `.gr.dart` and
   [3.2-AC5] fails.
3. **Then one contiguous, uninterrupted block: enum → router children → routes list
   → all six literals.** No `flutter analyze`, no `flutter test` and no commit
   between these. The enum goes first because it is the canonical order the other
   two are checked against. **This block matters more at five tabs than it did at
   four**: with the count unchanged there is no list-length disagreement anywhere
   to catch a half-applied reorder, so a check taken partway through reads a tree
   that looks consistent and is not.
4. **`build_runner` runs exactly once, at the end of that block.** It has one job
   here: regenerate `auto_route_config.gr.dart` ([3.2-AC5]). There is no second
   generation checkpoint — no new annotated model, no DI change, and neither new
   test uses `@GenerateMocks`.
5. **Tests, then the skill-file correction, then the baseline comparison.**

The intermediate tree does not analyze clean between steps 1 and GEN-2. That is
expected state per `generation.md`, not a failure, and must not consume a
self-correction attempt.

## Testing mode

**smoke** — rule matched: *UI-only with no new logic, isolated with no shared
dependencies.* No auth, no payments, no persistence, no offline queue, and the two
new widgets are throwaway shells with no data path.

Per `flutter-widget-test`'s "Decide whether to create a test file":

- **`LibraryScreen` — yes, one file**, `test/widget/library/library_screen_test.dart`
  ([3.2-AC29]), two tests. It owns navigation behaviour — an action that reports a
  tab index — which the skill names explicitly. The shell is throwaway; the index
  it hands Browse is not.
- **`FeedScreen` — yes, one file**, `test/widget/feed/feed_screen_test.dart`

- **The retired widgets — nothing to delete.** None of `saved_game_item.dart`,

Two tests for Library, one for Feed. Both files should stay at or under

## Caveats — claims I could not execute, with fallbacks

I have no Bash tool. Each of these is reasoned from source, not run; the Dev Agent
must record the outcome of each as a self-correction note either way.

**C-1 — the Library test needs a `TabsRouter` in scope, and the double is
hand-written.** `AutoTabsRouter.of(context)`
(`auto_route-11.1.0/…/auto_tabs_router.dart:150-162`) reads
`TabsRouterScope.of(context)` and *asserts* the scope is non-null, so pumping
`LibraryScreen` bare and tapping the action throws. Both `TabsRouterScope`
(`controller_scope.dart:135-151`, requires `controller` and `stateHash`) and
`TabsRouter` (`routing_controller.dart:634`, a plain non-`final` class) are exported
from `package:auto_route/auto_route.dart`. Plan: wrap the subject in
`TabsRouterScope(controller: fake, stateHash: 0, child: …)` with a file-private
`class _RecordingTabsRouter extends Fake implements TabsRouter` overriding only
`void setActiveIndex(int index, {bool notify = true})` to record the index.
  `RoutingController` declares a private member (`_parent`), which normally makes it
unimplementable from another library — `Fake`'s `noSuchMethod` is what makes it
legal, and that is the same mechanism Mockito's generated mocks rely on. I could not
compile it.
  This is a deliberate departure from `testing-conventions.md`'s "manual mock classes
are never written": that rule is written for project dependencies (repositories,
datasources, use cases, cubits), and the double here is for a third-party routing
controller with one method that matters.
  **Fallback if `Fake implements TabsRouter` will not compile:** switch to
`@GenerateNiceMocks([MockSpec<TabsRouter>()])` and add a `build_runner` run before
`flutter test`. **Second fallback if that also fails:** assert only the two render
criteria of [3.2-AC29], leave the tap assertion out, and escalate — do not weaken it
into a test that taps and asserts nothing.
  **This caveat does not reach the Feed test.** `FeedScreen` calls `setActiveIndex`
nowhere ([3.2-AC32]), so `test/widget/feed/feed_screen_test.dart` pumps the screen
inside a plain `MaterialApp` with the localisation delegates and needs no double at
all. If the Feed test acquires a `TabsRouterScope`, something has been copied from
the Library test that should not have been.

**C-2 — `build_runner` runs over a tree that does not fully resolve.** At the moment
of the single regeneration, `auto_route_config.gr.dart` still imports the two deleted
screen files, so the import graph has errors. This is the ordinary Flutter workflow
(write the annotated source, then generate) and `generation.md:24-25` sanctions it
explicitly. **Fallback if `build_runner` errors out rather than regenerating:**
delete `lib/config/route/auto_route_config.gr.dart` and re-run the same command; it
is a generated file and is rebuilt in full. Never hand-edit it, and never
hand-restore it ([3.2-AC5]).

**C-3 — `library` and `feed` as `S` members.** `library` is a Dart *built-in
identifier*, not a reserved word: it is barred from use as a type name, type
parameter or import prefix, and is legal as an ordinary member name, so
`String get library` and `S.current.library` should both compile ([3.2-AC22]).
`feed` is an ordinary identifier with no special status. I have not compiled either.
**Fallback, only if the generator or the analyzer actually rejects `library`:** rename
that key to `library_tab` in both `.arb` files and at its two call sites (the enum's
label switch and `library_screen.dart`), regenerate, and record it as a deviation.
Do not pre-emptively use `library_tab`, and do not touch `feed`.

**C-4 — the zh tab label may overflow, and D6 RAISED this risk.** At revision 1 I
reasoned that `游戏库` was safe because the cell had just got wider (four tabs
instead of five). **That reasoning is gone**: the count stays at five, so every cell
keeps its current width, and `游戏库` is a three-character label going into a cell
that has only ever held two-character ones (`精选`, `游戏`, `追踪`, `浏览`, `设置`).
`bottom_tab_bar_test.dart`'s *"renders every destination without overflow in zh at a
raised text scale"* case (`:245-266`) pumps `textScaleFactor: 2` and asserts
`tester.takeException()` is null, so an overflow fails there and nowhere else.
`动态` is two characters and carries no such risk.
  **Fallback if it overflows:** change the zh value of `library` to the
two-character `收藏`, which [3.2-AC19]'s own assumption names as the sanctioned
alternative. Do **not** widen the cell, change the label's text style, or touch the
tab bar's geometry — that is not this item's to change, and [3.2-AC2] forbids the
diff. Record which value shipped.

**C-5 — the tab-bar test's `tabLabel` numbers are correct and must be left alone.**
[3.2-AC26] keeps `tabLabel(tabIndex: 3, tabCount: 5)` at `:168-170` while retargeting
the surrounding finder from `S.current.tracker` to `S.current.browse`. That looks
wrong on a first read and is not: `MaterialLocalizations.tabLabel` is **1-based** —
`assert(tabIndex >= 1)` in the Flutter source — so `tabIndex: 3` names enum index 2,
which was Tracker and is now Browse. **Same slot, same numbers, only the label string
moves.** This was confirmed by reading the SDK source, not by running it, which is
the sanctioned method for a claim of this kind. **If the assertion nonetheless fails
at run time**, do not adjust the numbers by trial: the correct reading is
`tabIndex == destination.index + 1`, so re-derive from that one relation, apply it
once, and record it. Do not "correct" `:170` to a 0-based reading.

## Reuse decisions

- **`EmptyStateCard`** (`lib/widgets/empty_state_card.dart`) — the project's single
  empty-state component; `actionLabel` and `onActionPressed` are both required, so
  there is no actionless variant to fall back on and a dead button is not acceptable.
  The Library shell is its sixth call site. **Deliberately not reused by Feed**
  ([3.2-AC32]) — it would demand an action with no destination to send anyone to.
- **`DefaultSliverAppBar`** (`lib/widgets/default_sliver_app_bar.dart`) — the title
  treatment every tab-root screen already uses (`settings_screen.dart:55`,
  `games_screen.dart:170`, and the `browse_screen.dart` being deleted). Reused by
  both new screens rather than inventing a header the real screens will replace.
- **`GamesScreen` and its whole feature** — reused *as* Browse rather than rebuilt or
  renamed ([3.2-AC36]). This is the single largest saving D6 makes: slot 2 costs one
  string instead of a screen.
- **`no_games_saved` / `no_games_saved_description` / `browse_games`** — existing
  keys in both `.arb` files rather than new copy for Library. The first two are freed
  by `tracker_screen.dart:179-202`'s deletion and both hold English values in
  `intl_zh.arb`; `browse_games` gains a third caller ([3.2-AC20]).
- **`coming_soon`** — existing key in both `.arb` files for Feed's centred line, and
  it already carries a real Chinese value (`即将推出`, `intl_zh.arb:140`) rather than
  an English placeholder. Verified present in both locales. Its only other caller is
  `game_loading_data.dart:18`, where it stands in for an unknown release date — the
  words fit, the context differs, and minting `feed_coming_soon` is the fallback, not
  the default.
- **`browse`** — the l10n key is *kept*, not deleted, and now serves two callers: the
  enum's slot-2 label and `games_screen.dart:171`'s title. It already holds a real
  Chinese value (`浏览`).
- **`TrackerCubit`, `TrackerRepository`, `default_filter_list_app_bar.dart`,
  `default_alert_dialog.dart`** — all kept. The first three are orphaned by this
  item and item 3.4 reuses the tracker preferences plumbing; the fourth is **not**
  orphaned, `task_detail_screen.dart:319` still uses it and that file survives
  ([3.2-AC17]).

## Decisions for the human at the Phase 3 gate

The three glyphs are one enum line each and none blocks. The first is a genuine
conflict between two source documents and wants an explicit answer; the other two
are pure gaps where no document says anything.

1. **Slot 2 (Browse) — `Icons.search_outlined`, assumed, but this is a REAL
   DOCUMENT CONFLICT, not a gap.** The surviving `browse` enum value already carries
   `Icons.search_outlined` today (`bottom_tab_bar_destination.dart:8`), and
   [3.2-AC1] says that value "survives and is reused" — which reads as surviving
   intact, icon included. Against that, `handover.md` ruling 1 at `:893-894` says
   *"for now Games keeps its name and `Icons.gamepad_outlined`. Do not pre-emptively
   rename it or hand it `Icons.search_outlined`."* That sentence is **obsolete on its
   own premise** — its condition is "keeps its name", and D6 is precisely the
   decision that renames it — but it has not been struck from the file, so it is
   still a live-looking instruction pointing the other way. I have gone with
   `search_outlined` because the value that survives is `browse`, and because a
   search glyph matches the human's stated end state for this tab. **One line to
   overrule**, plus one fixture tuple ([3.2-AC24]) and one icon finder ([3.2-AC37]).
   If the human keeps `gamepad_outlined` instead, ruling 1's sentence should be
   struck anyway, because its first clause is false either way.
2. **Library — `Icons.collections_bookmark_outlined`, assumed.** No design document
   names it: `library-design-conventions.md:168` says only "Tab bar. Unchanged from
   Home", and `home-screen-design-conventions.md:108-115` gives sizes but no icon
   names. It matches the existing set's `_outlined` convention and reads as a saved
   collection rather than as books or video.
3. **Feed — `Icons.dynamic_feed_outlined`, assumed.** Same shape as the Library gap:
   `home-screen-design-conventions.md:117` mentions Feed only to say it keeps its
   tab. Same `_outlined` convention.

One further one-liner, unchanged from revision 1: **the Library shell's
`EmptyStateCard` gets no `glyph`.** It is the card's one optional parameter, no spec
names one for Library, and §11's real empty state (item 4.5) replaces this whole
card. Naming a glyph here would be invented design. Feed has no card at all.
