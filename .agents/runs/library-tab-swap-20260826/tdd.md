# Technical Design Document
Source: `.agents/runs/library-tab-swap-20260826/tech-ac.md` (Week 3 item 3.2 — Tab swap, Library shell, Tracker and Browse tab retirement)
Date: 2026-08-26

## Feature summary

A presentation-and-routing-only change. The bottom tab set goes from five to four
by rewriting three parallel declaration orders that must agree —
`BottomTabBarDestination`'s values, `AppRouter`'s `HomeRoute` children, and
`AutoTabsRouter`'s `routes:` list in `home_screen.dart` — and regenerating
`auto_route_config.gr.dart` from the second of them. Tab index is derived, never
declared, so the six hard-coded `setActiveIndex` literals are rewritten in the same
change and a seventh is introduced by a new throwaway `LibraryScreen`. Three source
files retire, three `.arb` keys change and the `S` class is regenerated by
`intl_utils`. No data, domain or state layer is added or touched.

## UI layer

### Screens

**`LibraryScreen` (create)** — `lib/features/library/presentation/screens/library_screen.dart`
— `StatelessWidget`, `@RoutePage()`, **`const` constructor**. Consumes nothing but
`S`. Structure: `Scaffold > SafeArea > CustomScrollView` with two slivers —
`DefaultSliverAppBar(title: S.current.library)` and a padded `SliverToBoxAdapter`
holding one `EmptyStateCard`. One interaction: the card's action calls
`AutoTabsRouter.of(context).setActiveIndex(2)` (Games). Navigates nowhere else. No
reactive boundary exists because there is no state.

The `const` constructor is load-bearing, not style: auto_route emits
`PageRouteInfo<void>` with no args class for a `const` screen (see `BrowseRoute` at
`auto_route_config.gr.dart:110-122`) and a `PageRouteInfo<XRouteArgs>` plus an args
class for a non-`const` one (see `TrackerRoute` at `:406-446`). A non-`const`
`LibraryScreen` still compiles but ships a pointless `LibraryRouteArgs`.

**`HomeScreen` (modify)** — `lib/features/home/presentation/screens/home_screen.dart:16-22`
— the `routes:` list becomes `FeaturedRoute(), LibraryRoute(), GamesRoute(),
SettingsRoute()` ([3.2-AC3]). Line `:27`'s
`onDestinationSelected: context.tabsRouter.setActiveIndex` tear-off is not touched
([3.2-AC7]).

**`FeaturedScreen` (modify)** — `:144`, `:145`, `:147`, `:207` literals → `2`
([3.2-AC6]). Nothing else in the file changes.

**Deleted:** `tracker_screen.dart`, `browse_screen.dart` (and the now-empty
`lib/features/browse/` tree) ([3.2-AC15]).

### The index literal set after this item

Eight `setActiveIndex` occurrences in `lib/`, seven carrying a literal ([3.2-AC8]):
the six rewritten sites, the `home_screen.dart:27` tear-off, and
`library_screen.dart`'s new `setActiveIndex(2)`. **Any check phrased "the count is
six" is a statement about the pre-change tree and fails a correct build.** Verified
at Phase 0 and re-verified here by grep: no other tab-index literal exists, and the
only other `activeIndex` hits are `ProgressDots`' onboarding dots ([3.2-AC9]).

`library_screen.dart` uses the bare literal `2` and must **not** import
`BottomTabBarDestination` to derive it. That enum is internal to the
`bottom_tab_bar/` module, whose single public surface is `BottomTabBar` — importing
it from a feature screen would be the same module-boundary violation item 2.4
shipped ten of.

## Ordering — the actual risk in this item

Three declaration orders must agree and one generated file is derived from one of
them. Sequence so no intermediate state can leave them disagreeing *at a point where
anything is checked*:

1. **`.arb` edits, then `intl_utils:generate`, first.** Everything downstream reads
   `S.current.library`, and the two deleted getters must be gone before the enum and
   the tab-bar test are rewritten to stop naming them.
2. **The new screen and the three deletions next.** `LibraryScreen` must exist with
   `@RoutePage()` before the router config names `LibraryRoute.page`, and
   `browse_screen.dart` / `tracker_screen.dart` must be *gone before* the router is
   regenerated — otherwise their `@RoutePage()` annotations keep emitting
   `BrowseRoute` / `TrackerRoute` / `TrackerRouteArgs` into `.gr.dart` and
   [3.2-AC5] fails.
3. **Then one contiguous, uninterrupted block: enum → router children → routes list
   → all six literals.** No `flutter analyze`, no `flutter test` and no commit
   between these. The enum goes first because it is the canonical order the other
   two are checked against.
4. **`build_runner` runs exactly once, at the end of that block.** It has one job
   here: regenerate `auto_route_config.gr.dart` ([3.2-AC5]). There is no second
   generation checkpoint — no new annotated model, no DI change, and the new test
   uses no `@GenerateMocks`.
5. **Tests last**, then the baseline comparison.

The intermediate tree does not analyze clean between steps 1 and 4. That is expected
state per `generation.md`, not a failure, and must not consume a self-correction
attempt.

## Testing mode

**smoke** — rule matched: *UI-only with no new logic, isolated with no shared
dependencies.* No auth, no payments, no persistence, no offline queue, and the one
new widget is a throwaway shell with no data path.

Per `flutter-widget-test`'s "Decide whether to create a test file":

- **`LibraryScreen` — yes, one file**, `test/widget/library/library_screen_test.dart`
  ([3.2-AC29]). It owns navigation behaviour (an action that reports a tab index),
  which the skill names explicitly. The shell is throwaway; the index it hands Games
  is not.
- **`BottomTabBarDestination` — no new file.** Its order is already asserted through
  the existing `bottom_tab_bar_test.dart`, which is the module's public surface. A
  second file asserting `.index` values would test the language, not the widget.
- **`BottomTabBar` and the four other module files — no new file and no edit.** They
  do not change ([3.2-AC2]).
- **`HomeScreen` — no test.** No test in the repository pumps it or asserts the tab
  route list, and adding one would need the full router graph for a list literal
  ([3.2-AC30]).
- **The retired widgets — nothing to delete.** None of `saved_game_item.dart`,
  `tracker_screen.dart` or `browse_screen.dart` has a test file.

Two tests are enough for the new file; more than that and it is longer than
`context_chip_test.dart`, which is the shape to copy. No `matchesGoldenFile`, here
or anywhere.

## Findings — corrections and additions to `tech-ac.md`

**TL-1 (must fix, missing from the criteria). `bottom_tab_bar_test.dart` needs
*two more* edits than [3.2-AC24]–[3.2-AC27] name, and both are silent
index-dependency failures of exactly the class this item exists to close.**

- `:90-108`, *"reports the tapped destination index once per tap"*, taps
  `S.current.games` three times and asserts `expect(reported, [1, 1, 1])`. The bar
  reports `destination.index`, and Games moves 1 → 2, so this must become
  `[2, 2, 2]`.
- `:110-155`, *"moves the selected state to the destination the caller supplies"*,
  pumps `selectedIndex: 1` and asserts Games is selected and Featured is not. Index
  1 is Library after the swap, so it must pump `selectedIndex: 2` to keep testing
  what it was written to test.

Both fail at run time, not compile time. `tech-ac.md` is not wrong about the four
edits it lists — it is incomplete, and [3.2-AC31]'s "no new failures" is the
criterion these two land under. The file is already allowlisted, so no scope change
is needed.

**TL-2 (deliberate non-change). `library_stats.dart:317` carries a second comment,
`// Go to Tracker detail for this game`.** It is not [3.2-AC10]'s comment, and it
still describes something real: `TrackerGameDetailRoute` and the push at `:319`
survive this item untouched ([3.2-AC4]). Leave it. Widget files carrying no comments
is the standing rule and this line breaks it, but removing it here is an
out-of-criteria edit to the same lines the protected task tree is reached through —
raise it as a follow-up, do not fold it in. Recorded so neither Dev nor QA has to
re-litigate it.

**TL-3 (third orphan, not named in the criteria). `RouteConstants.tracker`
(`lib/core/res/const.dart:62`) loses its last caller** with `tracker_screen.dart:125`,
joining `TrackerCubit` and `default_filter_list_app_bar.dart` ([3.2-AC17]). It is a
`static const` on a public class, so it produces no analyzer issue, and
`RouteConstants.featured` beside it is *already* unreferenced — the precedent for
leaving it is in the file itself. **Flagged, not deleted.** It is a hero-tag
`fromScreen` discriminator, unrelated to the `tracker` child route path this item
removes.

**TL-4 (documentation drift, out of scope, needs an orchestrator call).** After this
item, `.claude/skills/flutter-widgets/SKILL.md` describes a tree that no longer
exists in three places: `:160` and `:202` list `SavedGameItem` as legacy-but-live and
catalogue its deleted file, and the `BottomTabBar` entry says "five fixed
destinations at equal width … and a transparent cap on the other four". That is the
same stale-instruction shape item 3.1 exists to close, and the catalogue is read by
every future agent. It is **not in this item's allowlist** and I have not planned an
edit to it — a skill file is pipeline configuration, and the criteria do not cover
it. Raising it for the human at the Phase 3 gate.

## Caveats — claims I could not execute, with fallbacks

I have no Bash tool. Each of these is reasoned from source, not run; the Dev Agent
must record the outcome of each as a self-correction note either way.

**C-1 — the new test needs a `TabsRouter` in scope, and the double is hand-written.**
`AutoTabsRouter.of(context)` (`auto_route-11.1.0/…/auto_tabs_router.dart:150-162`)
reads `TabsRouterScope.of(context)` and *asserts* the scope is non-null, so pumping
`LibraryScreen` bare and tapping the action throws. Both `TabsRouterScope`
(`controller_scope.dart:135-151`, requires `controller` and `stateHash`) and
`TabsRouter` (`routing_controller.dart:634`, a plain non-`final` class) are exported
from `package:auto_route/auto_route.dart`. Plan: wrap the subject in
`TabsRouterScope(controller: fake, stateHash: 0, child: …)` with a file-private
`class _RecordingTabsRouter extends Fake implements TabsRouter` overriding only
`void setActiveIndex(int index, {bool notify = true})` to record the index.
  `RoutingController` declares a private member (`_parent`), which normally makes it
unimplementable from another library — `Fake`'s `noSuchMethod` is what makes it
legal, and that is the same mechanism Mockito's generated mocks rely on. I could not
compile it.
  This is a deliberate departure from `testing-conventions.md`'s "manual mock classes
are never written": that rule is written for project dependencies (repositories,
datasources, use cases, cubits), and the double here is for a third-party routing
controller with one method that matters. Generating `@GenerateNiceMocks([MockSpec<TabsRouter>()])`
would put Mockito codegen across auto_route's whole controller hierarchy on the
critical path of a throwaway shell's test.
  **Fallback if `Fake implements TabsRouter` will not compile:** switch to
`@GenerateNiceMocks([MockSpec<TabsRouter>()])` and add a `build_runner` run before
`flutter test`. **Second fallback if that also fails:** assert only the two render
criteria of [3.2-AC29], leave the tap assertion out, and escalate — do not weaken it
into a test that taps and asserts nothing.

**C-2 — `build_runner` runs over a tree that does not fully resolve.** At the moment
of the single regeneration, `auto_route_config.gr.dart` still imports the two deleted
screen files, so the import graph has errors. This is the ordinary Flutter workflow
(write the annotated source, then generate) and `generation.md:24-25` sanctions it
explicitly. **Fallback if `build_runner` errors out rather than regenerating:**
delete `lib/config/route/auto_route_config.gr.dart` and re-run the same command; it
is a generated file and is rebuilt in full. Never hand-edit it, and never
hand-restore it ([3.2-AC5]).

**C-3 — `library` as an `S` member.** `library` is a Dart *built-in identifier*, not
a reserved word: it is barred from use as a type name, type parameter or import
prefix, and is legal as an ordinary member name, so `String get library` and
`S.current.library` should both compile ([3.2-AC22]). I have not compiled it.
**Fallback, only if the generator or the analyzer actually rejects it:** rename the
key to `library_tab` in both `.arb` files and at its two call sites (the enum's label
switch and `library_screen.dart`), regenerate, and record it as a deviation. Do not
pre-emptively use `library_tab`.

**C-4 — the zh tab label may overflow.** `bottom_tab_bar_test.dart`'s *"renders every
destination without overflow in zh at a raised text scale"* case pumps `textScaleFactor: 2`.
`游戏库` is three characters against `游戏`'s two, in a cell that just got wider (four
tabs, not five), so it should pass. **Fallback if it overflows:** change the zh value
to the two-character `收藏`. Do **not** widen the cell or touch the tab bar's geometry
— that is not this item's to change.

## Reuse decisions

- **`EmptyStateCard`** (`lib/widgets/empty_state_card.dart`) — the project's single
  empty-state component; `actionLabel` and `onActionPressed` are both required, so
  there is no actionless variant to fall back on and a dead button is not acceptable.
  The Library shell is its sixth call site.
- **`DefaultSliverAppBar`** (`lib/widgets/default_sliver_app_bar.dart`) — the title
  treatment every tab-root screen already uses (`settings_screen.dart:55`,
  `games_screen.dart:170`, and the `browse_screen.dart` being deleted). Reused rather
  than inventing a header the real Library screen will replace anyway.
- **`no_games_saved` / `no_games_saved_description` / `browse_games`** — existing
  keys in both `.arb` files rather than new copy. The first two are freed by
  `tracker_screen.dart:179-202`'s deletion and both hold English values in
  `intl_zh.arb`; `browse_games` gains a third caller ([3.2-AC20]).
- **`TrackerCubit`, `TrackerRepository`, `default_filter_list_app_bar.dart`,
  `default_alert_dialog.dart`** — all kept. The first three are orphaned by this
  item and item 3.4 reuses the tracker preferences plumbing; the fourth is **not**
  orphaned, `task_detail_screen.dart:319` still uses it and that file survives
  ([3.2-AC17]).

## Decisions for the human at the Phase 3 gate

Both are one-line changes and neither blocks. Recorded here rather than as open
questions because the pipeline can proceed on either answer.

1. **The Library tab glyph is `Icons.collections_bookmark_outlined`, assumed.** No
   design document names it — `library-design-conventions.md:168` says only "Tab bar.
   Unchanged from Home", and `home-screen-design-conventions.md:108-115` gives sizes
   for a five-tab IA that ruling 1 supersedes. It matches the existing set's
   `_outlined` convention and reads as a saved collection. Overruling it changes one
   enum line and one tuple in `bottom_tab_bar_test.dart`.
2. **The shell's `EmptyStateCard` gets no glyph.** `glyph` is the card's one optional
   parameter, no spec names one for Library, and §11's real empty state (item 4.5)
   replaces this whole card. Naming a glyph here would be invented design.
